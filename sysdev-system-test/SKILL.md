# システムテスト（＋セルフ受け入れ・完了）

**目的**: 完成したシステムが、要件定義書のすべての要件を満たすことを確かめ、プロジェクトを完了させる。
**入力**: 要件定義書（受け入れ基準・非機能要件）、結合テストを完了したシステム
**成果物**:

- `docs/08_system_test/システムテスト仕様書兼結果.md`
- `docs/08_system_test/完了報告書.md`
- `docs/00_project/振り返り.md`

## 手順

### 1. テストケースの設計

- **機能要件**: `REQ-F` ごとの受け入れ基準を、`ST-001` 形式のケースにする。ペルソナの1日の業務を想定したシナリオで、通しで確認する（例: 朝の期限チェック → 発注 → 入荷登録）。
- **非機能要件**: `REQ-NF` ごとに確認方法を決める。
  - 性能: 主要な画面の表示時間を計測する（ブラウザの DevTools など）。
  - セキュリティ: リポジトリ全体と、ブラウザに届く通信の中に、APIキーが含まれていないか確認する。
    リポジトリの確認例: `git log -p | grep -i <キーの一部>`
  - 可用性: 外部APIを止めても（無効なキーを設定するなど）、アプリ全体が落ちないか確認する。
  - ドメイン: アレルゲンなどの表示に免責文言が出ているか確認する。
- **環境**: README の手順で、まっさらな環境から立ち上げたものでテストする（できれば別ディレクトリへ clone し直す）。

### 2. 実施・記録

- 結合テストと同じ形式で、結果と証跡を残す。
- NG になったら原因の工程を特定し、修正・回帰テストを行う。計画内に直せないものは「既知の不具合」として完了報告書に書く。

### 3. セルフ受け入れチェック（受け入れテストの代わり）

クライアントの立場に立ち、PJ計画書の **成功基準** と要件定義の **目的** に照らして判定する。

- [ ] ペルソナの課題は解決されたか（As-Is → To-Be が実現できたか）
- [ ] 成功基準をデモで示せるか
- [ ] Must の要件をすべて満たしたか

### 4. 完了報告・振り返り

- **完了報告書**: 次の内容をまとめる。
  - 実施内容
  - 要件ごとの達成状況
  - 品質（各テストの件数・不具合件数・カバレッジ）
  - 既知の不具合と制約
  - 予定と実績の比較（工程別）
- **振り返り（KPT）**:
  - Keep: 続けたいこと
  - Problem: 問題だったこと
  - Try: 次に試すこと
  - 見積もりと実績の差がどの工程で大きかったかと、その理由

## システムテスト仕様書兼結果テンプレート

```markdown
# システムテスト仕様書兼結果 v1.0
## 1. 方針・環境
## 2. テストケース
| ST-ID | 要件ID | 区分(機能/非機能) | シナリオ・手順 | 期待結果（受け入れ基準） | 結果 | 実施日 | 証跡 |
|---|---|---|---|---|---|---|---|
## 3. セルフ受け入れチェック結果
## 4. 結果サマリ・既知の不具合
```

## 省略可

- 負荷テスト・長時間稼働テスト（個人利用の想定なら対象外と明記する）
- 正式なリリース判定会（セルフ受け入れチェックで代える）

## 完了条件（ゲート）

- [ ] すべての Must の要件に ST ケースがあり、結果が OK
- [ ] すべての REQ-NF について、確認結果（または対象外）がある
- [ ] まっさらな環境から起動してテストした
- [ ] セルフ受け入れチェックの全項目を満たした
- [ ] トレーサビリティ表のすべての行が、要件から ST までつながっている
- [ ] 完了報告書と振り返りを作成した

## Claude向けメモ

- トレーサビリティ表に、テストのない要件や、要件のないテストが残っていたら指摘する。
- 完了後に作業を続ける場合（Should の機能を追加する、など）は、`sysdev-overview` に戻って小さく工程を回すよう案内する。
