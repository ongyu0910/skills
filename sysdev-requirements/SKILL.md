# 要件定義

**目的**: 「何を作るか（What）」を確定させる。ここで決めた要件が、システムテストの合否基準になる。
**入力**: `docs/00_project/システム構想書.md`（なければ先に `sysdev-concept` を使う）、`docs/00_project/PJ計画書.md`（なければ先に `sysdev-overview` を使う）
**成果物**: `docs/01_requirements/要件定義書.md`

## 手順

### 0. 要求の整理（省略した要求定義の代わり）

クライアントがいないため、自分で「架空のクライアント」を立てる。システム構想書で決めた利用者・課題・提供価値を出発点にして、次の粒度まで具体化する。

- **ペルソナ**: 誰が（例: 個人経営の惣菜店の店長、従業員3名）、どんな場面で使うか。
- **現状の課題（As-Is）**: 今どう作業していて、何に困っているか。可能なら数値で書く（例: 毎朝30分かけて期限を目視で確認している）。
- **あるべき姿（To-Be）**: システムを入れると、何がどう変わるか。
- 業務フローを As-Is / To-Be の2枚で、Mermaid の flowchart で描く。

### 1. 機能要件

- To-Be の業務フローの各ステップから、「システムが何をするか」を抽出し、`REQ-F-001` 形式で番号を振る。
- 外部APIを使う要件には、どのデータを取りにいくかを書く（APIの選定は全体設計で行う）。
- 各要件に **MoSCoW**（Must / Should / Could / Won't）を付ける。Must は、PJ計画で決めた開発規模に収まる数に抑える。

### 2. 非機能要件

プロジェクトの規模に合わせて、項目は最小限にする。ただし、項目自体は落とさずに「対象外」と明記する。

| 区分           | 例                                                          |
| -------------- | ----------------------------------------------------------- |
| 性能           | 画面表示2秒以内（API呼び出しを含む場合は5秒以内）           |
| 可用性         | ローカル動作のみ／外部APIが停止しても、アプリ自体は落ちない |
| セキュリティ   | APIキーは環境変数で管理する。入力値を検証する               |
| 運用・保守     | 起動手順を README に記載する                                |
| 移行           | 対象外（新規構築のため）                                    |
| 法令・ドメイン | アレルゲン等の表示に免責文言を出す                          |

### 3. 制約・前提・スコープ外

- 制約: 予算・使用技術の縛り・体制・利用形態（Web／スマホ／デスクトップ など）
- スコープ外（Won't）: ログイン／決済／本番運用 など、明示的に「やらない」と書く

### 4. 受け入れ基準

- Must の要件ごとに「どうなれば完了か」を1行で書く。これがシステムテスト（`ST-xxx`）の元になる。

## 要件定義書テンプレート

```markdown
# 要件定義書 v1.0
| 版 | 日付 | 変更内容 |
|---|---|---|

## 1. 背景・目的 / ペルソナ
## 2. 業務フロー（As-Is / To-Be）
## 3. 機能要件
| ID | 要件 | 優先度(MoSCoW) | 受け入れ基準 | 外部API利用 |
|---|---|---|---|---|
| REQ-F-001 | 食材を登録できる | Must | 品名・数量・期限を登録し、一覧に表示される | - |
## 4. 非機能要件
| ID | 区分 | 要件 | 基準値 |
|---|---|---|---|
## 5. 制約・前提
## 6. スコープ外（Won't）
## 7. 用語集
```

## 省略可

- 用語集（ドメインの用語が少なければ省く）
- As-Is 業務フロー（課題を文章で十分に説明できれば省く）

## 完了条件（ゲート）

- [ ] ペルソナ・課題・目的が1ページで説明できる
- [ ] すべての機能要件に ID・MoSCoW・受け入れ基準がある
- [ ] Must の要件だけで「使える」最小構成（MVP）になっている
- [ ] Must の総量が、PJ計画で想定した開発規模に収まる見込みがある
- [ ] 外部APIで実現する要件が特定されている
- [ ] 非機能要件の全区分に、記載または「対象外」がある
- [ ] スコープ外が明記されている
- [ ] トレーサビリティ表に要件ID列を作成した

## Claude向けメモ

- ペルソナ・課題・Must の範囲は、ユーザーの判断事項。案は出すが、必ず確認をとる。
- Must が多すぎる場合は、Should に下げる候補を具体的に提案する。
- 終わったら `sysdev-architecture` へ進むよう案内する。
