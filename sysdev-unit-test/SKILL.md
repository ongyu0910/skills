# 単体テスト

**目的**: 各モジュール（MOD）が、詳細設計どおりに単独で動くことを確かめる。
**進め方**: テストコードは実装と並行して書き、実装完了後に全件を消化・修正する
**入力**: 詳細設計書（単体テスト観点）、ソースコード
**成果物**: テストコード、`docs/06_unit_test/単体テスト仕様書兼結果.md`

## 手順

### 1. テストケースの設計

詳細設計の「単体テスト観点」を、具体的なケース（`UT-001`）に展開する。

- **同値分割**: 有効な値のグループと無効な値のグループから、それぞれ代表値を1つずつ選ぶ。
- **境界値分析**: 境界の前後をテストする（例: 賞味期限が「今日」「明日」「昨日」、数量が 0／1／上限／上限+1）。
- **異常系**: 必須項目が空、型が違う、DBエラー。
- **外部APIクライアント**: 正常レスポンス、データなし、タイムアウト、4xx/5xx、想定外の形式 → それぞれ設計どおりに振る舞うか。

### 2. 外部APIのモック化

- 単体テストでは、本物の外部APIを **呼ばない**（レート制限を消費しない、結果がぶれない、ネットワークに依存しない、という理由）。
- 全体設計のスパイクで保存したサンプル（`docs/02_architecture/api-samples/`）を、モックのレスポンスとして使う。

### 3. 実行・記録

- テストフレームワーク（pytest / Vitest / Jest など）で自動実行する。カバレッジも計測する。
- 目標の目安: 業務ロジック（サービス層）は行カバレッジ80%以上。UI層は対象外としてよい。
- 失敗したケースは、修正 → 再実行の記録を残す（バグ数は品質指標になる）。

## 単体テスト仕様書兼結果テンプレート

```markdown
# 単体テスト仕様書兼結果 v1.0
## 1. 対象・方針（対象MOD、モック方針、カバレッジ目標）
## 2. テストケース
| UT-ID | MOD-ID | 観点 | 入力・前提 | 期待結果 | 結果(OK/NG) | 実施日 | テストコード |
|---|---|---|---|---|---|---|---|
| UT-001 | MOD-005 | 境界値：期限=今日 | expiry=today | 「期限当日」に分類される | OK | 2026-01-15 | test_expiry.py::test_today |
## 3. 結果サマリ（件数、OK/NG、カバレッジ、バグ件数）
## 4. 不具合一覧（ID / 内容 / 原因 / 対応 / 再テスト結果）
```

## 省略可

- 単純な CRUD やフレームワーク標準機能のテスト
- ケース表の「テストコード」列（テスト関数名と UT-ID を一致させるなら省く）

## 完了条件（ゲート）

- [ ] 詳細設計のすべての単体テスト観点がケース化されている
- [ ] 全ケースを実行し、NG がゼロ（または修正済みで、再テストが OK）
- [ ] 外部APIの異常系のケースがすべて OK
- [ ] カバレッジの目標を達成した（未達なら理由を記録した）
- [ ] トレーサビリティ表の UT 列を更新した

## Claude向けメモ

- テストコードを書くときは、テスト関数名かコメントに UT-ID を入れる。
- 終わったら `sysdev-integration-test` へ進むよう案内する。
