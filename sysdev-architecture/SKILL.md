# 全体設計

**目的**: 「どういう仕組みで作るか（How の大枠）」を決める。技術選定とAPI選定に関わるリスクを、この工程でつぶしておく。
**入力**: `docs/01_requirements/要件定義書.md`
**成果物**: `docs/02_architecture/全体設計書.md`

## 手順

### 1. システム構成

- 構成要素（フロントエンド／バックエンド／DB／外部API）と、そのつながりを Mermaid で描く。各要素に `ARC-001` 形式の ID を振る。
- 小規模・個人開発なら、**構成要素はできるだけ少なくする**。例えば次のような構成にする。
  - Webアプリ1つ（フロントとバックエンドを一体にする。例: Next.js、または Flask/FastAPI＋テンプレート）＋ SQLite ＋ 外部API
  - バックエンド経由で外部APIを呼ぶ（APIキーをブラウザに出さないため）

### 2. 技術スタックの選定

選定理由とあわせて表にする。判断基準は「自分が使い慣れているか」「計画した規模で完成できるか」を最優先にする。

| 区分                                   | 採用 | 理由 | 代替案 |
| -------------------------------------- | ---- | ---- | ------ |
| 言語 / FW / DB / テスト / ホスティング |      |      |        |

### 3. 外部APIの選定（重要）

候補ごとに次の項目を確認し、表にまとめる。

| 確認項目                 | 内容                                                                 |
| ------------------------ | -------------------------------------------------------------------- |
| 提供データ               | 要件（`REQ-F-xxx`）を満たすか                                      |
| 認証                     | 不要／APIキー／OAuth（OAuth は実装負荷が高いので、小規模なら避ける） |
| 料金・無料枠・レート制限 | 開発中とデモ時の呼び出し回数で足りるか                               |
| 利用規約                 | 商用利用・データの保存・表示クレジットの要否                         |
| 安定性・日本語対応       | 日本の食品データがどの程度あるか                                     |

**スパイク（技術検証）**: 採用候補のAPIを実際に `curl` などで1回呼び、レスポンスのサンプルを `docs/02_architecture/api-samples/` に保存する。ここで動かなければ、すぐ代替案に切り替える。

### 4. 非機能要件の実現方式

要件定義の `REQ-NF-xxx` ごとに、どう実現するかを書く。

- 外部APIが失敗した場合: タイムアウト（例: 5秒）、エラー表示、必要ならキャッシュを使う
- APIキー: `.env` に置き、`.gitignore` 対象にする。`.env.example` を用意する
- ログ: 出力先とレベル（個人開発ならコンソールとファイルで十分）

### 5. 開発標準・構成管理

- Git のブランチ戦略（個人開発なら `main` ＋ 作業ブランチで十分）とコミットメッセージのルール
- ディレクトリ構成の方針
- コーディング規約（Linter/Formatter の採用で代える）

## 全体設計書テンプレート

```markdown
# 全体設計書 v1.0
## 1. システム構成図（Mermaid）
## 2. 構成要素一覧（ARC-ID / 役割 / 技術）
## 3. 技術スタックと選定理由
## 4. 外部API選定結果（比較表・採用理由・利用条件・スパイク結果）
## 5. 非機能要件の実現方式（REQ-NF との対応）
## 6. 開発環境・構成管理・開発標準
## 7. リスクと対策（API停止、レート制限、技術の習熟不足 など）
```

## 省略可

- 代替案の詳細な比較（採用理由が明確なら1行でよい）
- インフラ構成（ローカル動作のみの場合）

## 完了条件（ゲート）

- [ ] 構成図があり、すべての構成要素に ARC-ID がある
- [ ] 技術スタックがすべて決まり、選定理由がある
- [ ] 外部APIを実際に呼んで、必要なデータが取れることを確認した（サンプルを保存済み）
- [ ] API の利用規約・無料枠・レート制限を確認した
- [ ] APIキーの管理方法が決まっている
- [ ] すべての REQ-NF に実現方式（または対象外）が書かれている
- [ ] トレーサビリティ表を更新した

## Claude向けメモ

- API の料金・規約・レート制限は変わることがある。記憶で答えず、公式ドキュメントを確認する（またはユーザーに確認してもらう）。
- 技術選定はユーザーの習熟度に強く左右されるため、使い慣れた言語を必ず確認する。
- 終わったら `sysdev-basic-design` へ進むよう案内する。
