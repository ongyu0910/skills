# システム開発 全体ガイド

個人開発のシステム開発プロジェクトの「地図」となるスキル。前提条件は次のとおり。
PJ計画書（`docs/00_project/`）を作り、各工程スキルへ案内する。

## 前提条件

| 項目     | 内容                                                                   |
| -------- | ---------------------------------------------------------------------- |
| PJ内容   | プロジェクトごとに `sysdev-concept` で決める（システム構想書に記載） |
| 期間     | プロジェクトごとに決める（PJ計画書に記載）                             |
| 技術条件 | 簡単な外部APIを1つ以上使う                                             |
| 開発手法 | ウォーターフォール（V字モデルで工程とテストを対応させる）              |
| 体制     | 個人（発注者＝開発者＝テスター）。クライアントはいない                 |

## 工程と担当スキル

```
システム構想 → (要求定義) → 要件定義 → 全体設計 → 基本設計 → 詳細設計 → 開発/実装 → 単体テスト → 結合テスト → システムテスト → (受け入れテスト)
```

| # | 工程                 | スキル                                                             | 主な成果物                                             | 対応するテスト（V字）    |
| - | -------------------- | ------------------------------------------------------------------ | ------------------------------------------------------ | ------------------------ |
| 0 | システム構想         | `sysdev-concept`                                                 | システム構想書（業界・テーマ／利用者／課題／提供価値） | -                        |
| - | 要求定義             | **省略**（要件定義の「0. 要求の整理」に吸収）                | -                                                      | （受け入れテスト）       |
| 1 | 要件定義             | `sysdev-requirements`                                            | 要件定義書                                             | システムテスト           |
| 2 | 全体設計             | `sysdev-architecture`                                            | 全体設計書（構成図・技術選定・API選定）                | システムテスト（非機能） |
| 3 | 基本設計（外部設計） | `sysdev-basic-design`                                            | 基本設計書（画面・機能・DB論理・API IF）               | 結合テスト               |
| 4 | 詳細設計（内部設計） | `sysdev-detailed-design`                                         | 詳細設計書（モジュール・テーブル定義・処理）           | 単体テスト               |
| 5 | 開発/実装            | `sysdev-implementation`                                          | ソースコード・実装記録                                 | -                        |
| 6 | 単体テスト           | `sysdev-unit-test`                                               | 単体テスト仕様書兼結果                                 | ← 詳細設計              |
| 7 | 結合テスト           | `sysdev-integration-test`                                        | 結合テスト仕様書兼結果                                 | ← 基本設計              |
| 8 | システムテスト       | `sysdev-system-test`                                             | システムテスト仕様書兼結果・完了報告                   | ← 要件定義              |
| - | 受け入れテスト       | **省略**（システムテストの「セルフ受け入れチェック」で代替） | -                                                      | -                        |

**省略の方針**: クライアントが存在しいないため、要求定義と受け入れテストは省略する。
ただし **工程そのものは飛ばさない**。各工程の完了条件（ゲート）は必ず確認する。

## スケジュール管理

期間はプロジェクトごとに異なるため、このスキルでは固定の日数を決めない。PJ計画時に次の手順で計画を立てる。

1. 開発期間と、単位あたりの作業時間（例: 平日2h・休日5h）をユーザーに確認し、PJ計画書に書く。
2. 期間を工程ごとに配分する。配分は次を目安に調整する。
   - 設計（要件定義〜詳細設計）と、実装・テスト（実装〜システムテスト）の比率は、おおよそ 4:6
   - 全体の約15%をバッファとして、最後に確保する
   - 単体テストのコードは、実装と並行して書く
3. 工程ごとに、予定と実績を記録する。
4. 遅れがバッファを食いつぶしそうになったら、スコープを見直す（MoSCoW の Could → Should の順に削る）。

## ドキュメント構成（開発対象リポジトリ内）

```
docs/
  00_project/        システム構想書.md / PJ計画書.md / トレーサビリティ表.md / 課題・変更管理表.md / 振り返り.md
  01_requirements/   要件定義書.md
  02_architecture/   全体設計書.md
  03_basic_design/   基本設計書.md
  04_detailed_design/詳細設計書.md
  05_implementation/ 実装記録.md
  06_unit_test/      単体テスト仕様書兼結果.md
  07_integration_test/結合テスト仕様書兼結果.md
  08_system_test/    システムテスト仕様書兼結果.md / 完了報告書.md
```

- すべて Markdown で書き、図は Mermaid で描く（Git で差分を追えるようにするため）。
- 文書の先頭には、版数・更新日・変更履歴を必ず付ける。

## ID体系とトレーサビリティ

ID で前後の工程をつなぎ、「要件 → 設計 → コード → テスト」の抜け漏れを防ぐ。

| 種別                                | ID形式                                               | 作る工程     |
| ----------------------------------- | ---------------------------------------------------- | ------------ |
| 機能要件 / 非機能要件               | `REQ-F-001` / `REQ-NF-001`                       | 要件定義     |
| 方式・構成要素                      | `ARC-001`                                          | 全体設計     |
| 画面 / 機能 / 外部API IF / テーブル | `SCR-001` / `FN-001` / `API-001` / `TBL-001` | 基本設計     |
| モジュール                          | `MOD-001`                                          | 詳細設計     |
| テストケース                        | `UT-001` / `IT-001` / `ST-001`                 | 各テスト工程 |

`docs/00_project/トレーサビリティ表.md` は、各工程の終わりに1列ずつ追加して更新する。

```markdown
| 要件ID | 画面/機能ID | API/テーブルID | モジュールID | UT | IT | ST |
|---|---|---|---|---|---|---|
| REQ-F-001 | SCR-001, FN-001 | API-001 | MOD-003 | UT-001〜005 | IT-002 | ST-001 |
```

## PJ計画書テンプレート（`docs/00_project/PJ計画書.md`）

```markdown
# PJ計画書 v1.0
## 1. PJ概要
- PJ名（システム名） / システムの一言説明（「〇〇が、〇〇できるシステム」）
- 背景・目的 / 想定利用者（ペルソナ）（システム構想書から要約して転記する）
- 成功基準（例: 〇〇の作業時間を半分にする、をデモで示せる）
## 2. スコープ
- やること（MVP） / やらないこと（明記する）
## 3. 前提・制約
- 期間・作業時間 / 使用API / 予算（原則0円。APIの無料枠に収める）
## 4. スケジュール（工程ごとの予定・実績。「スケジュール管理」の手順で作る）
## 5. 成果物一覧
## 6. 品質方針（各工程のゲート、レビュー方法）
## 7. リスクと対策
## 8. 構成管理（Git運用、ブランチ、ドキュメントの置き場所）
```

## 追加で考慮すべき項目（指定条件以外）

1. **テーマとスコープの確定**: `sysdev-concept` で1つの課題と1人のペルソナに絞ってから計画に入る。テーマが広いまま計画すると、要件が膨らむ。
2. **外部APIのリスク**: 利用規約・商用利用の可否・レート制限・無料枠・データの正確性・停止時の挙動を、全体設計で必ず確認する。APIキーはリポジトリに含めない（`.env` ＋ `.gitignore`）。
3. **ドメイン特有の注意**: 対象業界の法令・ガイドライン・表示ルール、扱う情報の正確性に関する免責表示、個人情報の有無を、要件定義で洗い出す。法令は改正されるため、最新の情報を公的機関の発表で確認する。
4. **個人開発ならではの品質確保**: レビューする人がいないため、各工程の完了条件チェックリストでセルフレビューする。Claude にレビュー役を頼むのも有効。
5. **変更管理**: 手戻りが出たら、前の工程の文書を修正し、版数を上げて `課題・変更管理表.md` に記録する。ウォーターフォールでも、記録を残せば手戻りは許容する。
6. **環境**: ローカル開発環境の再現手順（README）。デプロイするかどうかはスコープで決める（小規模ならローカル動作＋デモで十分）。
7. **振り返り**: 最後に KPT（Keep / Problem / Try）を `振り返り.md` に残す。見積もりと実績の差も記録する。

## このスキルの使い方（Claude向け）

1. `docs/` があるか確認し、どの工程まで終わっているかを、成果物の有無と各文書の完了条件チェックで判定する。
2. `docs/00_project/システム構想書.md` がなければ、先に `sysdev-concept` でシステムの概要（業界・テーマ、利用者、課題、提供価値）を決める。
3. `docs/00_project/PJ計画書.md` がなければ、システム構想書をもとに、上のテンプレートでユーザーと対話しながら作る。期間・作業時間・スコープ（MVP）は、必ずユーザーに確認する。
4. 現在の工程に対応する `sysdev-*` スキルを使って作業を進める。
5. 工程が終わるたびに、トレーサビリティ表とスケジュールの実績を更新する。
