# 詳細設計（内部設計）

**目的**: そのまま実装に移れるレベルまで、内部の作りを決める。ここで決めたことが、単体テストの基準になる。
**入力**: 基本設計書、全体設計書
**成果物**: `docs/04_detailed_design/詳細設計書.md`

## 手順

### 1. モジュール構成

- ディレクトリツリーを書き、ファイル・クラス・モジュールごとに `MOD-001` 形式の ID を振る。
- 責務を分ける。目安は次の4層。
  - 画面（UI）
  - ルーティング/コントローラ
  - サービス（業務ロジック）
  - リポジトリ（DB）／外部APIクライアント
- **外部APIクライアントは1モジュールに閉じ込める**。こうすると、単体テストでモックに差し替えやすく、APIを替えるときの影響も小さくなる。

### 2. テーブル定義（物理設計）

`TBL-xxx` ごとに次の表を作る。DDL（`CREATE TABLE`）またはマイグレーションの形でも書いておく。

| 物理名 | 論理名 | 型 | NULL | PK/FK | デフォルト | 備考 |
| ------ | ------ | -- | ---- | ----- | ---------- | ---- |

- インデックスと、日付の扱い（賞味期限は日付型にする。タイムゾーンは JST 固定など）を決める。

### 3. 内部API・関数仕様

- 内部APIごとに、パス・メソッド・リクエスト・レスポンス（正常／異常）・ステータスコードを書く。
- 主要な関数は、シグネチャ（引数・戻り値・例外）と処理概要を書く。全関数を書く必要はない。業務ロジックを持つものに絞る。

### 4. 外部API呼び出しの詳細

- タイムアウト値、リトライの有無と回数、レスポンスの変換（DTO）、キャッシュの有無、レート制限への対策。
- 異常系: タイムアウト／4xx／5xx／想定外の形式／データなし。それぞれのとき、どう振る舞うか（`MSG-xxx` との対応）。

### 5. 処理フロー

- 複雑な処理（例: 期限が近い食材の抽出、APIデータとDBデータの統合）は、Mermaid の `sequenceDiagram` か `flowchart` で描く。

### 6. 共通方針

- 入力チェックをどこで行うか、例外処理の方針、ログ（何を・どのレベルで出すか。APIキーや個人情報は出力しない）。

### 7. 単体テストの観点を作る（V字モデル）

- `MOD` ごとに、テスト観点（正常系／異常系／境界値）を箇条書きにする。

## 詳細設計書テンプレート

```markdown
# 詳細設計書 v1.0
## 1. ディレクトリ・モジュール構成（MOD-ID / 責務 / 対応FN）
## 2. テーブル定義（TBL ごと）＋ DDL
## 3. 内部API仕様
## 4. 主要関数仕様
## 5. 外部API呼び出し詳細（タイムアウト・リトライ・変換・異常系）
## 6. 処理フロー図
## 7. 共通方針（バリデーション・例外・ログ）
## 8. 単体テスト観点（MOD ごと）
```

## 省略可

- 単純な CRUD 関数の個別の仕様（「標準 CRUD」とまとめて書けばよい）
- クラス図（モジュール構成の表で足りるなら省く）

## 完了条件（ゲート）

- [ ] すべての FN が、1つ以上の MOD に対応している
- [ ] すべてのテーブルに、物理定義と DDL がある
- [ ] 外部APIの異常系（タイムアウト・エラー・データなし）の振る舞いが決まっている
- [ ] 外部APIクライアントが独立したモジュールになっていて、モックに差し替えられる
- [ ] 単体テスト観点を作成した
- [ ] 「この設計書だけを見て実装を始められるか」をセルフチェックした
- [ ] トレーサビリティ表にモジュールID列を追加した

## Claude向けメモ

- 使うフレームワークの慣習（ディレクトリ構成など）に合わせる。フレームワークに逆らう独自構成は避ける。
- 終わったら `sysdev-implementation` へ進むよう案内する。
