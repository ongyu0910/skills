# 開発/実装

**目的**: 詳細設計どおりに動くコードを作る。単体テストのコードも並行して書く。
**入力**: 詳細設計書、基本設計書、全体設計書
**成果物**: ソースコード、`README.md`（起動手順）、`docs/05_implementation/実装記録.md`

## 手順

### 1. 環境構築（実装の最初に行う）

- リポジトリの作成、`.gitignore`、`.env.example`、Linter/Formatter の設定、テストフレームワークの導入。
- 「Hello World ＋ 外部APIを1回呼ぶ」までを最初に通しておく（いわゆる歩くスケルトン）。

### 2. 実装順序の計画

次の順で、1機能ずつ「縦に」完成させていく。

1. DB（マイグレーション／DDL）とリポジトリ層
2. 外部APIクライアント（`MOD` の1つ。スパイクのサンプルを使ってテストも書く）
3. Must の機能を、業務フローの順に（サービス → コントローラ → 画面）
4. Should の機能（余裕があれば）

実装記録に、計画と実績を書く。計画より遅れが出たら、`sysdev-overview` のスコープ見直しルールに従う。

### 3. コーディングのルール

- 1つの作業単位を1ブランチ・1コミットのまとまりにする。コミットメッセージに `FN-xxx` / `MOD-xxx` を入れる（トレーサビリティのため）。
- 設計書と食い違う実装が必要になった場合:
  1. 設計書を先に直し、版数を上げる
  2. `課題・変更管理表.md` に記録する
  3. そのあとで実装する（ウォーターフォールの基本）
- APIキーやパスワードはコードに書かない。コミット前に `git diff` で確認する。

### 4. セルフコードレビュー

機能が1つ完成するたびに、次の観点で確認する（Claude にレビューを頼んでもよい）。

- 設計どおりか（MOD の責務・I/F・メッセージ）
- 異常系（入力不正・API失敗）を処理しているか
- 秘密情報やデバッグ用コードが残っていないか
- Linter の警告がゼロか

## 実装記録テンプレート

```markdown
# 実装記録
## 進捗
| 日付 | 予定(FN/MOD) | 実績 | 差異・メモ |
|---|---|---|---|
## 設計からの変更
| 日付 | 対象（設計書・ID） | 内容 | 理由 |
|---|---|---|---|
## 課題・メモ（ハマった点、次回への学び）
```

## 省略可

- 正式なコードレビュー記録表（コミットとセルフレビュー観点のチェックで代える）

## 完了条件（ゲート）

- [ ] Must のすべての FN が実装済みで、ローカルで動く
- [ ] README の手順どおりに、ゼロから起動できる
- [ ] Linter の警告ゼロ。秘密情報がコミットされていない
- [ ] 設計からの変更が、すべて設計書と実装記録に反映されている
- [ ] 単体テストのコードが、主要な MOD について書かれている

## Claude向けメモ

- 実装を頼まれたら、先に該当する MOD／FN の設計書の該当箇所を読んでからコードを書く。
- 設計にない機能を足そうとしない。必要なら、変更管理として提案する。
- 終わったら `sysdev-unit-test` へ進むよう案内する。
