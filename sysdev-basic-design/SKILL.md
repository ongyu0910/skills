# 基本設計（外部設計）

**目的**: 利用者（とシステムの外側）から見たときの振る舞いを確定させる。ここで決めたことが、結合テストの基準になる。
**入力**: 要件定義書、全体設計書
**成果物**: `docs/03_basic_design/基本設計書.md`

## 手順

### 1. 機能一覧

- 要件（`REQ-F`）を、システムの機能単位（`FN-001`）に分ける。1つの要件が複数の機能になってもよい。
- 機能ごとに、対応する要件ID・画面ID・使う外部APIを書く。

### 2. 画面設計

- **画面一覧**: `SCR-001` 形式。画面数は、Must の要件を満たす最小限に抑える。
- **画面遷移図**: Mermaid の `flowchart` か `stateDiagram` で描く。
- **画面レイアウト**: 項目名・入力形式・必須かどうか・入力チェック・ボタンとその動作を表にする。ワイヤーフレームは手書きの写真や簡単なASCII図で十分。

### 3. DB論理設計

- エンティティと関係を Mermaid の `erDiagram` で描く。テーブルには `TBL-001` 形式の ID を振る。
- この段階では論理名と主な属性だけを決める（型や制約は詳細設計で決める）。
- 外部APIから取得したデータを保存するかどうかを決める（利用規約を確認すること）。

### 4. 外部インターフェース設計

- 外部APIごとに `API-001` 形式の ID を振り、次の項目を決める。
  - 使うエンドポイント
  - 送るパラメータ
  - 受け取る項目（レスポンスのうち使うものだけ）と、それを画面・DBのどの項目に当てはめるか（マッピング）
  - 失敗したときの画面上の振る舞い
- 自分で API（バックエンドのエンドポイント）を作る場合も、ここで一覧にする（パス・メソッド・用途）。

### 5. メッセージ一覧

- エラー・確認・完了のメッセージに `MSG-001` 形式の ID を振る。外部APIの失敗時やアレルゲンの免責表示の文言も含める。

### 6. 結合テストの観点を作る（V字モデル）

- 画面遷移と、各機能をまたぐ流れ（登録 → 一覧 → API取得 → 表示 など）から、結合テストの観点を箇条書きにしておく。

## 基本設計書テンプレート

```markdown
# 基本設計書 v1.0
## 1. 機能一覧
| FN-ID | 機能名 | 概要 | 要件ID | 画面ID | API-ID |
|---|---|---|---|---|---|
## 2. 画面一覧・画面遷移図
## 3. 画面レイアウト（画面ごと）
### SCR-001 食材一覧
| 項目 | 種別 | 必須 | 入力チェック | 備考 |
|---|---|---|---|---|
| ボタン | 動作 | 遷移先 |
## 4. DB論理設計（ER図・エンティティ定義）
## 5. 外部インターフェース（API-ID / エンドポイント / 項目マッピング / 失敗時の振る舞い）
## 6. 内部API一覧（自作する場合）
## 7. メッセージ一覧
## 8. 結合テスト観点
```

## 省略可

- 帳票設計（帳票がなければ省く）
- バッチ設計（定期処理がなければ省く）
- 画面レイアウトの画像（項目の表があれば足りる）

## 完了条件（ゲート）

- [ ] Must のすべての要件が、1つ以上の FN／SCR に対応している
- [ ] 画面遷移図に、行き止まりや到達できない画面がない
- [ ] 全画面に、入力項目・入力チェック・ボタンの動作が定義されている
- [ ] ER図があり、すべてのテーブルに TBL-ID がある
- [ ] 外部APIの項目マッピングと、失敗時の振る舞いが決まっている
- [ ] 結合テストの観点を作成した
- [ ] トレーサビリティ表に画面/機能ID と API/テーブルID の列を追加した

## Claude向けメモ

- 要件にない画面や機能を追加しそうになったら、要件定義書の変更（変更管理表への記録）として扱うか、Won't に回すかをユーザーに確認する。
- 終わったら `sysdev-detailed-design` へ進むよう案内する。
