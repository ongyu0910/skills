# システム構想（システムの概要を決める）

**目的**: プロジェクトの土台として、システムの一般的な概要（業界・テーマ、利用者、課題、提供価値）を、ユーザーとの質問と回答で決める。
**入力**: なし（ユーザーの頭の中にあるアイデア。アイデアがなくてもよい）
**成果物**: `docs/00_project/システム構想書.md`
**次の工程**: `sysdev-overview`（PJ計画）→ `sysdev-requirements`（要件定義）

## このフェーズで決めること

| 項目         | 内容                                                  |
| ------------ | ----------------------------------------------------- |
| 業界・テーマ | どの業界・領域の、どんなテーマのシステムか            |
| 利用者       | 誰が、どんな場面で使うか（1人の具体的な人物像に絞る） |
| 課題         | 利用者が今どうしていて、何に困っているか              |
| 提供価値     | システムによって、利用者の何がどう良くなるか          |

## このフェーズで決めないこと

上の4項目以外は決めない。下記の話題が出た場合、「後の工程で決める」と伝え、システム構想書の「後工程への申し送り」にメモだけして先に進む。

| 決めないこと                                                                   | 決める工程                             |
| ------------------------------------------------------------------------------ | -------------------------------------- |
| システム名、システムの一言説明                                                 | PJ計画（`sysdev-overview`）          |
| 期間・スケジュール、作業時間、成功基準、スコープ（MVP）                        | PJ計画（`sysdev-overview`）          |
| 機能、扱うデータ、やらないこと、受け入れ基準                                   | 要件定義（`sysdev-requirements`）    |
| 外部APIで得たい情報                                                            | 要件定義（`sysdev-requirements`）    |
| 利用形態（Web／スマホ／デスクトップ など）、性能・セキュリティなどの非機能要件 | 要件定義（`sysdev-requirements`）    |
| 具体的な外部APIの選定、技術スタック、システム構成                              | 全体設計（`sysdev-architecture`）    |
| 画面、DB、外部APIとの接続方法                                                  | 基本設計（`sysdev-basic-design`）    |
| モジュール構成、テーブル定義、処理の流れ                                       | 詳細設計（`sysdev-detailed-design`） |

## 進め方（質問と回答のルール）

1. **1回の質問は2〜3問まで**にする。全部まとめて聞かない。ラウンドごとに回答を受け取り、次へ進む。
2. **回答しやすい形で聞く**。可能なら選択肢（2〜4個。おすすめに「（おすすめ）」と付ける）を出し、自由回答も受け付ける。
   - `AskUserQuestion` ツールが使える環境ではそれを使う。
   - 使えなければ、チャットで番号付きの質問として聞く。
3. **前の回答を踏まえて次の質問を作る**。下の質問リストは骨組み。回答に応じて言い換え、掘り下げ、省略をしてよい。
4. **「わからない」「おまかせ」と言われたら**、それまでの回答から具体的な候補を2〜3個出し、選んでもらう。Claude が勝手に決めない。
5. **回答があいまいなら1回だけ掘り下げる**（例:「効率化したい」→「どの作業の、何に時間がかかっていますか？」）。それでも決まらなければ、未決事項として残す。
6. 各ラウンドの終わりに、決まったことを1〜2行で復唱する。

## 質問リスト（ラウンド構成）

### ラウンド1: 業界・テーマ

- Q1. どの業界・領域のシステムを作りたいですか？（例: 飲食、小売、教育、医療・介護、物流、社内業務、個人の生活 など）
- Q2. その中で、どんなテーマを扱いたいですか？（決まっていなければ、ラウンド2・3の回答から候補を出す）

### ラウンド2: 利用者

- Q3. 誰が使いますか？（立場、人数、ITへの慣れ）
- Q4. その人は、どんな場面で使いますか？

### ラウンド3: 課題

- Q5. その人は、何に困っていますか？
- Q6. 今はその困りごとを、どうやってしのいでいますか？（紙、Excel、既存アプリ、我慢している など）

### ラウンド4: 提供価値

- Q7. システムがあると、その人の何がどう良くなりますか？（例: 〇〇にかかる時間が減る、〇〇のミスがなくなる）

### 最終確認

- 4項目を、下のテンプレートの形で要約して見せ、「この内容で確定してよいか」を確認する。
- 修正があれば反映し、確定したら `docs/00_project/システム構想書.md` に書き出す。

## システム構想書テンプレート

```markdown
# システム構想書 v1.0
| 版 | 日付 | 変更内容 |
|---|---|---|

## 1. 業界・テーマ
## 2. 利用者
- 人物像（立場・人数・ITへの慣れ）
- 利用する場面
## 3. 課題
- 現状（今どうしているか）
- 困りごと
## 4. 提供価値
## 5. 未決事項・後工程への申し送り
## 6. 質問と回答の記録
| ラウンド | 質問 | 回答 |
|---|---|---|
```

## 完了条件

- [ ] 1〜4 の4項目が埋まっている（埋まらない項目は、理由とあわせて 5 に記載）
- [ ] 利用者が1人の具体的な人物像に絞られている
- [ ] 提供価値が、課題（3）の解決につながっている
- [ ] ユーザーが要約を確認し、「確定」と回答した
- [ ] 質問と回答の記録が残っている

## Claude向けメモ

- このフェーズの主役はユーザー。Claude は質問役と、案を出す役に徹する。
- 既に `docs/00_project/システム構想書.md` がある場合は、内容を読み、埋まっていない項目だけを質問する。
- 確定したら、`sysdev-overview` で PJ計画を立てるよう案内する。
